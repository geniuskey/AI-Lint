# 문서간 추적성

문서 하나만 잘 써도 안 되는 문제가 있습니다. 요구사항 REQ-42를 설계 문서가 참조하는데 그 요구사항 문서가 어디에도 없거나, 두 문서가 같은 REQ-42를 서로 다르게 적어놓은 경우입니다. 이런 건 문서 한 장을 아무리 들여다봐도 보이지 않습니다.

추적성 분석은 **검사한 문서 전체**를 그래프로 보고 이런 문제를 찾습니다.

## 인덱스는 어떻게 쌓이나

별도의 크롤러가 없습니다. `POST /v1/lint`가 성공할 때마다 그 문서가 인덱스에 들어갑니다.

```
POST /v1/lint  ──→  리포트 반환
       └────────→  추적성 인덱스 갱신 (부수 효과)
```

이 설계에는 결과가 따릅니다.

- **검사한 문서만 코퍼스에 있습니다.** 아무도 검사하지 않은 문서는 없는 것과 같습니다. TRC001과 TRC005의 메시지가 "인덱스에 없습니다"라고 말하는 이유입니다 — 정말 없는 것일 수도, 아직 검사하지 않은 것일 수도 있습니다.
- **백엔드는 여전히 문서를 가지러 가지 않습니다.** 크롤러를 두면 위키 자격 증명이 필요해지고 권한 경계가 무너집니다.
- **인덱스 갱신이 실패해도 검사는 성공합니다.** 실패는 경고 로그로만 남고 리포트는 그대로 나갑니다.

인덱스에 남는 것은 문서 URI, 제목, 유형, 해시, 수정 시각, 식별자 언급, 내부 링크뿐입니다. 각 언급에는 그 식별자가 나온 블록의 발췌가 붙는데 기본 400자에서 잘립니다. 문서 원문은 저장되지 않습니다.

## 식별자 인식

기본 패턴은 세 가지입니다.

| kind | 정규식 | 예 |
|---|---|---|
| `requirement` | `REQ-\d+` | REQ-42 |
| `test` | `TC-\d+` | TC-7 |
| `ticket` | `[A-Z]{2,10}-\d+` | PROJ-1234 |

앞선 패턴이 이깁니다. `REQ-42`는 ticket 패턴에도 걸리지만 requirement로 남습니다.

**정의와 참조를 구분합니다.** 이 판단이 그래프의 방향을 정합니다.

- 문서 **제목**에 나오면 정의로 봅니다.
- **제목 블록**(heading)에 나오면 정의로 봅니다.
- 문서 유형이 `requirement`이고 requirement 종류의 식별자면, 본문 어디에 나와도 정의로 봅니다.
- 그 외에는 참조입니다.
- 자기가 정의한 식별자는 자기 참조로 세지 않습니다.

## 룰

`TRC001`~`TRC006`은 **문서 점수에 들어가지 않습니다.** 코퍼스 상태에 따라 판정이 달라지는 룰을 단일 문서 점수에 섞으면, 남이 문서를 안 올렸다는 이유로 내 문서 등급이 떨어집니다. 그래서 별도 리포트로만 나갑니다.

| ID | 심각도 | 무엇을 잡나 |
|---|---|---|
| TRC001 | error | 정의되지 않은 식별자를 참조 |
| TRC002 | warning | 설계 문서가 요구사항을 참조하지 않음 |
| TRC003 | warning | 요구사항에 연결된 테스트가 없음 |
| TRC004 | error | 같은 식별자를 두 문서가 정의 |
| TRC005 | info | 링크 대상 문서가 인덱스에 없음 |
| TRC006 | error | 같은 식별자에 대한 서술이 서로 어긋남 (LLM) |

TRC003의 판정은 "REQ-42를 참조하는 문서들 중 테스트 식별자를 가진 것이 하나도 없다"입니다. 테스트 문서가 요구사항을 참조하는 실제 관행을 따른 것입니다.

## 상충 탐지 (TRC006)

앞의 다섯은 그래프만 보면 결정됩니다. TRC006은 두 문서가 같은 것을 두고 **다른 말을 하는지** 읽어야 알 수 있어서 LLM이 필요합니다.

문서를 전부 대조하면 문서 수의 제곱으로 늘어납니다. 그래서 후보를 좁힙니다.

1. **같은 식별자를 다루는 문서 쌍만** 후보가 됩니다.
2. 공유 식별자가 많은 쌍부터 정렬합니다.
3. 상위 `maxPairs`(기본 20)개만 실제로 대조합니다.
4. 잘렸으면 리포트에 `truncated: true`가 붙고, `stats.pairsConsidered`와 `stats.pairsAnalyzed`로 몇 개 중 몇 개를 봤는지 알려줍니다.

모델에는 두 문서의 **발췌만** 보냅니다. 그리고 판정할 때 양쪽에서 인용한 문장을 함께 내게 합니다. 그 문장이 실제 발췌에 있는지 대조해서, 없으면 그 지적을 버립니다. 확신도가 0.6 미만인 것도 버립니다. 버린 개수는 `stats.llmFindingsRejected`에 남습니다.

모델에게 명시적으로 금지한 것들:

- 표현만 다르고 뜻이 같으면 상충이 아니다
- 한쪽에만 있는 내용은 상충이 아니다
- 수치, 조건, 책임 주체가 실제로 어긋날 때만 보고한다

동시 호출은 3개로 제한하고, 쌍 하나가 실패해도 나머지는 계속합니다. 전부 실패하면 결정적 판정 다섯 개만이라도 돌려줍니다.

## 쓰는 법

데스크톱 앱의 **추적성** 탭에서 실행합니다.

![추적성 탭. 문서 4개, 식별자 6개에서 5건의 지적. TRC001·TRC003·TRC004·TRC005·TRC006이 표로 나열되어 있다](/shots/desktop-trace.png)

*식별자가 어느 문서에서 정의되고 어디서 참조되는지를 그래프로 본 결과입니다.*

1. "코퍼스 조회"를 누르면 `POST /v1/trace/analyze`가 호출됩니다.
2. "AI 대조 사용"을 끄면 TRC006 없이 결정적 판정만 돕니다.
3. 결과를 HTML이나 Excel로 내보냅니다.

API로 직접 부를 수도 있습니다.

```bash
curl -s http://localhost:8787/v1/trace/analyze \
  -H 'content-type: application/json' \
  -H "x-ai-lint-token: $SERVICE_TOKEN" \
  -H 'x-ai-lint-user: me' \
  -d '{"useLlm": true}' | jq
```

응답 구조는 [HTTP API](/reference/api#post-v1-trace-analyze)를 보세요.

## 쿼터

LLM 대조도 문서 검사와 같은 일일 한도를 씁니다. 요약이나 유형 추론 같은 부수 호출까지 세므로, 한도가 실제 호출 수를 반영합니다. 한 번도 부르지 않았으면 쿼터를 소모하지 않습니다.

한도에 걸리면 `llmStatus: 'skipped'`, `llmSkipReason: 'quota'`로 나오고 결정적 판정만 담깁니다.
